# Android experience audit

Reviewed 6 September 2026 against v0.3.9, commit b06b18c346a45afe5504ccceb4c6ec5f35976ce9. The findings below describe that original source snapshot; the initial audit did not change application code.

The focused [keyboard fix plan](SAMSUNG_KEYBOARD_FIX_PLAN.md) now records the authorized emulator-based repair and its validation. Samsung hardware is unavailable, so Samsung callback capture and APK inspection are deferred. The actual-app emulator baseline subsequently reproduced the illustrative duplication sequence described below.

The highest-value improvement is a reliable bridge between Android text editing and remote keyboard input. Keep useful autocorrect, gesture typing and dictation. The existing app already has a strong native foundation: Compose/Material 3, adaptive layouts, system/dynamic themes, biometric credential access, layered Back handling and accessible viewport controls. A visual or architecture rewrite is not justified by these findings.

**What explains the keyboard symptom**

The app exposes an invisible text editor, retains composing text locally, forwards each commit as new remote keystrokes, then clears its local text. Android keyboards can also finish composition, replace a selection, reopen a previous word, or delete around the cursor. Those paths are not equivalent in the current bridge. Android's [InputConnection contract](https://developer.android.com/reference/android/view/inputmethod/InputConnection) defines composition, selection, cursor positioning and batch notifications as part of editing; simply forwarding commit arguments does not implement that model.

A normal composition corrected by commit already works. Composition-completion and deletion paths produce errors in the callback harness, which is consistent with an intermittent problem. Replacement traces additionally show the effect of discarded local context; they do not reproduce a particular keyboard's correction sequence.

The user reports **stock Samsung Keyboard on One UI 8.5**: autocorrect usually applies correctly, but occasionally the host receives both the originally typed word and the correction. This makes replacement/deletion handling the first reproduction target. The host application and the exact Samsung callback sequence remain unknown.

One concrete mechanism consistent with that symptom is: commit “teh ”; delete four code points backwards; commit “the ”. The first commit sends “teh ” and clears the local editable. The inherited code-point deletion then has no retained text to delete and emits no remote Backspaces. The final commit appends “the ”, producing “teh the ”. This combined sequence is an illustrative deduction from the individually reproduced commit and code-point deletion behavior, not a captured Samsung trace. Lost composing-region context is another candidate; the symptom alone does not distinguish them.

Samsung describes Auto replace as completing or replacing a word when Space or Enter is used. That supports testing those boundaries, but does not document the keyboard's internal InputConnection calls or establish a One UI-specific defect. See [Samsung's keyboard guidance](https://www.samsung.com/uk/support/mobile-devices/how-can-i-personalise-and-turn-predictive-text-on-and-off-on-my-samsung-galaxy-device/).

**Recommended input design**

Keep ordinary typing live. Let Android manage a real editable state with composition and selection, using a standard editor where it can replace custom plumbing. [Compose text fields](https://developer.android.com/develop/ui/compose/text/user-input) already manage these local editing concepts. Keep remote text transient and scoped to the current foreground session.

The bridge must distinguish pending local composition from text submitted to the transport. The current KVM path exposes video and HID input, with no host editor text or caret readback. A local text buffer therefore cannot become an authoritative copy of the host document. Only consider replacing recently sent text while its tracked context remains valid; clear that context after pointer/caret movement, control shortcuts, session changes, layout changes or uncertain transmission. External keyboards and host-side formatting remain limitations to evaluate on a real host.

Preflight the entire proposed edit, including its replacement text, before sending any Backspaces. Reuse the existing HID mapper and the paced-paste path's reject-before-send behavior. Preserve rejected text in an accessible unsent draft with clear feedback. Do not silently remove accents or punctuation. Any optional punctuation conversion should be visible to the user.

Preflight cannot make remote editing transactional: a disconnect can interrupt HID transmission. Expose admission/failure outcomes to the editor, invalidate uncertain context and retain the existing no-replay policy. A successful transport send does not prove the remote application accepted the intended text.

Keep physical HID input and the existing special-key controls. A modifier shortcut must be a deliberate key operation; never turn the rest of an autocorrected word into additional shortcuts or continue sending it after a shortcut changes the target.

A compact, optional Compose text surface could later support full local editing before sending, including editable clipboard/share previews. It would preserve autocorrect and dictation without needing to revise already transmitted text. It is a separate UX choice with draft lifecycle work; do not require a Send tap for every normal word or add multiple typing modes before repairing the existing path.

**Implementation sequence and acceptance checks**

1. Prioritize the Samsung report: a correction leaves exactly one corrected word; undo restores exactly one original word, with surrounding text intact and autocorrect enabled. Define recent-context, shortcut, invalidation and transport-failure rules before implementing remote replacements. Add focused tests at the real app input-connection boundary, including commit → code-point delete → corrected commit, then fix local composition completion, deletion semantics, cursor state and connection invalidation. Include working composition-at-commit as a regression baseline. Existing keyboard instrumentation only tests a simple ASCII commit and explicitly requires NO_SUGGESTIONS.
2. Implement remote edit translation under those rules, with complete preflight and recoverable failure feedback. Test curly apostrophes, accents, supplementary characters, unsupported replacements and failures between HID reports. Rejected text remains recoverable; no part of an invalid edit reaches the host, and uncertain transmission is never replayed.
3. Enable suggestions for natural text after those safeguards pass. Test stock Samsung Keyboard on One UI 8.5 first, with Auto replace kept enabled, followed by Gboard and SwiftKey for compatibility. Cover autocorrect on Space/Enter, accepting a suggestion, correction undo, gesture typing, dictation, punctuation, Tab, held Backspace, cursor movement, physical shortcuts, hide/reopen, rotation, background and reconnect. Exercise both US and UK host layouts. Confirm the resulting text in a disposable editor on a real host. If the callback path needs identifying, use synthetic sample words and record event types, edit lengths and selection/composition offsets without retaining ordinary typed content.
4. Fix touch movement and gesture ownership independently; add form keyboard actions. Validate compact/landscape layouts, large text and accessibility. Consider optional composition UI and tap-latency changes only after those improvements.

**Evidence and limits**

The audit combines source review, independent input/transport/UX reviews and current official Android documentation. A small standalone Android 37 callback harness exercised Android's actual BaseInputConnection with the relevant app overrides reproduced in Java. It was not the installed app, a specific keyboard, or a remote-host test. Synthetic results were:

| Callback sequence | Observed forwarded events |
| --- | --- |
| Compose “hello”; finish; commit a space | Space only |
| Compose a misspelling; commit corrected “the ” | Corrected text, as intended |
| Delete zero characters | One Backspace |
| Delete one character forwards | One Backspace |
| Commit “ab”; delete one code point backwards | “ab” only; deletion returned success |
| Commit “cat”; select its former range; commit “dog” | Both strings appended; the selected range is stale in the cleared local editable |
| Direct commit callback after close | Text forwarded; framework dispatch was not simulated |

The default full-editor composition behavior is also documented in [BaseInputConnection](https://developer.android.com/reference/android/view/inputmethod/BaseInputConnection#finishComposingText()). Detailed synthetic traces remain in the ignored local audit scratch directory. The reused disposable emulator was stopped afterward. No host was controlled, no APK was rebuilt or published, and no application code changed for this audit.
